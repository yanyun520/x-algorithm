# 06 · 推荐打分与排序策略

> 核心知识点:**多动作预测的概率加权**、负向信号建模、**作者多样性衰减**算法、网内/网外内容平衡、双阶段过滤的成本哲学。

源码位置:`home-mixer/scorers/`、`home-mixer/filters/`、`home-mixer/selectors/top_k_score_selector.rs`。

---

## 1. 打分链:四个 Scorer 的职责接力

```rust
let scorers = vec![
    phoenix_scorer,            // ① ML 推理:产出 15+ 动作概率
    weighted_scorer,           // ② 概率加权和 → weighted_score
    author_diversity_scorer,   // ③ 按作者衰减 → score
    oon_scorer,                // ④ 网外折扣 → 最终 score
];
```

链式结构让每个 scorer 只做一件事,且顺序有严格语义:先拿到原始预测,再合成单一分数,再做业务调整(多样性、来源偏好)。**调整类 scorer 必须在合成分数之后**,因为它们操作的是最终分。

## 2. 多动作加权:把"用户会做什么"翻译成"该排第几"

Phoenix 模型不输出单一相关性,而是预测 15+ 种动作概率。`WeightedScorer` 将其合成:

$$\text{Score} = \sum_i w_i \cdot P(\text{action}_i)$$

```rust
let combined_score = Self::apply(s.favorite_score, p::FAVORITE_WEIGHT)
    + Self::apply(s.reply_score, p::REPLY_WEIGHT)
    + Self::apply(s.retweet_score, p::RETWEET_WEIGHT)
    + /* ... 正向动作 ... */
    + Self::apply(s.not_interested_score, p::NOT_INTERESTED_WEIGHT)   // 负权重
    + Self::apply(s.block_author_score, p::BLOCK_AUTHOR_WEIGHT)       // 负权重
    + Self::apply(s.mute_author_score, p::MUTE_AUTHOR_WEIGHT)         // 负权重
    + Self::apply(s.report_score, p::REPORT_WEIGHT);                  // 负权重
```

学习要点:

- **负向动作显式建模**:不是"预测喜欢",而是同时预测"拉黑/屏蔽/举报"的概率并赋负权重——用户可能讨厌的内容被直接压下去,这比只优化正向指标更能控制 feed 质量;
- **权重与模型解耦**:模型重训不改权重,运营调权重不重训模型——策略迭代成本极低;
- **条件权重**:`vqv_weight_eligibility` 对时长足够(> `MIN_VIDEO_DURATION_MS`)的视频才启用"有效观看"权重,避免短视频刷分;
- **分数整形**(`offset_score`):利用正/负权重和把合成分映射到含偏移的区间,保证不同量级分数可比、且负分内容能被正确排到末尾。

## 3. 作者多样性衰减:防刷屏的数学

如果某作者有多条高分帖,不加干预会霸占 feed。`AuthorDiversityScorer` 的做法:

1. 按 `weighted_score` 降序遍历候选;
2. 维护每个作者已出现的次数 `position`(第 0 条、第 1 条...);
3. 乘上衰减因子:

$$m(p) = (1 - \text{floor}) \cdot d^p + \text{floor}$$

```rust
fn multiplier(&self, position: usize) -> f64 {
    (1.0 - self.floor) * self.decay_factor.powf(position as f64) + self.floor
}
```

- 第 0 条:$m = 1$(不衰减,最佳帖不受损);
- 随后按 $d^p$ **指数衰减**;
- `floor` 保底:无论第几条,最多衰减到 `floor` 倍,不会归零(该作者内容极相关时仍有机会)。

**为什么按排序后位置衰减而不是按候选顺序**:衰减必须作用于"该作者的第 k 高分帖",只有先按分数排序遍历,`author_counts` 计数才代表"第 k 好的帖"——否则衰减对象会被候选输入顺序随机化。同时用 `original_idx` 把调整后的分数写回原位置,保持与框架"等长同序"的契约。

## 4. OON 折扣:来源偏好的表达

```rust
let updated_score = c.score.map(|base_score| match c.in_network {
    Some(false) => base_score * p::OON_WEIGHT_FACTOR,   // 网外乘折扣系数
    _ => base_score,
});
```

网外内容(OON)天然没有"我关注了他"这一强信号,同等预测分下应略降权——这是用乘法系数表达业务先验的最简方式。

## 5. 双阶段过滤:成本决定位置

| 阶段 | 过滤器 | 设计原因 |
|------|--------|----------|
| 打分前 | 去重、年龄、自己帖、RT 去重、订阅资格、已看过、已推送、屏蔽词、社交图 | 廉价规则先行,**省掉对无效候选的 ML 推理** |
| 选择后 | VF(删除/垃圾/暴力)、会话去重 | VF 判定昂贵,只对 TopK 后的少量候选执行 |

注意 `PreviouslyServedPostsFilter` 与 side effect 的闭环:`CacheRequestInfoSideEffect` 在请求结束后把本次推送的帖 ID 异步写缓存,下次请求据此过滤——**跨请求状态通过 side effect 流转,不阻塞在线响应**。

## 6. TopK 选择:契约最小化

```rust
impl Selector<ScoredPostsQuery, PostCandidate> for TopKScoreSelector {
    fn score(&self, candidate: &PostCandidate) -> f64 {
        candidate.score.unwrap_or(f64::NEG_INFINITY)  // 未打分沉底
    }
    fn size(&self) -> Option<usize> { Some(params::TOP_K_CANDIDATES_TO_SELECT) }
}
```

排序与截断逻辑全部由 trait 默认方法提供(见文档 02);`NEG_INFINITY` 兜底保证"没拿到分数的候选"自然排到末尾而不是随机位置。

## 7. 可迁移场景

- **任何多目标排序**(电商、广告、内容):多概率加权 + 负向信号 + 条件权重;
- **Feed 多样性治理**:按排序位置指数衰减 + floor 保底,是 LinkedIn/Twitter 都在用的经典方案;
- **成本敏感的多阶段系统**:"廉价规则前置、昂贵判定后置"的过滤器布局原则。
