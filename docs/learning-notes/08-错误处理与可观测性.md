# 08 · 错误处理与可观测性

> 核心知识点:**组件级容错**(局部失败不拖垮整体)、错误的分级处置、结构化日志的 request_id 贯穿、防御性不变量校验、指标埋点模式。

---

## 1. 容错的分层:哪里该降级,哪里该失败

整个项目对错误的处置是**有意识分级**的,可归纳为一张决策表:

| 错误场景 | 处置 | 出处 |
|----------|------|------|
| 单个 hydrator/scorer/filter 失败 | `error!` 记录,跳过该组件,流水线继续 | `candidate_pipeline.rs` |
| 单个 filter 失败 | 回滚到备份候选,继续后续 filter | `run_filters` |
| hydrator 返回长度不匹配 | `warn!` 跳过合并,保留原候选 | `run_hydrators` |
| Kafka poll 瞬时错误 | 记指标 + 100ms 退避重试 | `tweet_events_listener_v2.rs` |
| 单批消息反序列化失败 | `warn!` 丢批继续 | 同上 |
| 消费线程永久退出 | **panic**(fail-fast) | 同上 |
| 请求参数非法(viewer_id=0) | 立即返回 `INVALID_ARGUMENT` | `server.rs` |

**决策原则**:问"继续运行还有意义吗?"
- 缺一路特征/少一个过滤 → feed 质量略降但仍可用 → **降级继续**;
- 数据流永久中断 → 服务活着但已腐坏 → **立即 panic 触发重启**。

## 2. 结构化日志:request_id 贯穿全链路

框架在每个阶段、每个组件的日志中都注入统一上下文:

```rust
info!(
    "request_id={} stage={:?} component={} fetched {} candidates",
    request_id, PipelineStage::Source, source.name(), candidates.len()
);
error!(
    "request_id={} stage={:?} component={} failed: {}",
    request_id, PipelineStage::QueryHydrator, hydrator.name(), err
);
```

- `request_id` 来自 `HasRequestId` trait——泛型约束要求查询类型**必须**提供稳定请求标识,编译期保证可追踪性;
- `PipelineStage` 枚举让"哪个阶段"成为结构化字段而非自由文本;
- `component` 名来自组件 trait 的默认 `name()`(反射类型短名),零手写成本。

服务端首尾呼应:

```rust
info!("Scored Posts request - request_id {}", query.request_id);
info!("Scored Posts response - request_id {} - {} posts ({} ms)", ...);
```

一次请求从进入到返回的完整轨迹(各阶段成功/失败/耗时)可以用一个 request_id 全部捞出。

## 3. 防御性不变量校验

**(a) 长度契约**:`run_hydrators` 要求水合结果与输入等长,否则拒绝合并:

```rust
if hydrated.len() == expected_len {
    hydrator.update_all(&mut candidates, hydrated);
} else {
    warn!("... skipped: length_mismatch expected={} got={}", ...);
}
```

长度不匹配意味着水合结果与候选错位,盲目 `zip` 会把 A 帖的特征写到 B 帖上——**宁可缺特征,不可错特征**。

**(b) Scorer 的文档契约**:"不允许在 scorer 中丢候选,丢候选请用 Filter"——把不变量写进 trait 文档,配合长度校验双重防护。

**(c) 入参校验前置**:`viewer_id == 0` 在 handler 入口直接拒绝,不让脏请求进入流水线空转。

## 4. 指标埋点:Prometheus 风格

thunder 的指标设计值得模仿——**围绕业务问题设计指标,而不是只埋技术计数器**:

```rust
GET_IN_NETWORK_POSTS_FOUND_FRESHNESS_SECONDS   // 返回的帖有多新鲜?
GET_IN_NETWORK_POSTS_FOUND_REPLY_RATIO         // 回复占比多少?
GET_IN_NETWORK_POSTS_FOUND_UNIQUE_AUTHORS      // 覆盖了多少作者?
GET_IN_NETWORK_POSTS_FOUND_POSTS_PER_AUTHOR    // 每作者平均几帖?
```

这些指标直接回答"召回质量健不健康"的业务问题;并且用 `stage` label 对比不同阶段(post_store 捞出时 vs 最终返回时)的分布变化,**过滤链路的信息损耗可视化**:

```rust
fn analyze_and_report_post_statistics(posts: &[LightPost], stage: &str) {
    GET_IN_NETWORK_POSTS_FOUND_REPLY_RATIO.with_label_values(&[stage]).observe(reply_ratio);
    // ...
}
```

此外:`IN_FLIGHT_REQUESTS`/`REJECTED_REQUESTS` 观测信号量限流是否过紧;`KAFKA_POLL_ERRORS` 观测消费健康度;`POST_STORE_*` 系列观测内存库存量与命中。

## 5. 宏埋点与低开销采样

- `#[xai_stats_macro::receive_stats]`:用属性宏给打分器、handler 自动包一层耗时/计数统计——**横切关注点用宏注入**,业务代码零侵入;
- 高频路径的日志用原子计数器每 1000 次采样一次(见文档 03),避免日志本身成为瓶颈。

## 6. 可迁移场景

- 任何多组件流水线:错误分级决策表 + 组件级容错模板;
- 微服务排障体系:request_id + stage + component 的结构化日志三要素;
- 数据管道的质量保障:长度/错位防御校验,"缺数据优于错数据"原则;
- 推荐/搜索系统的指标体系:按 stage label 观测各阶段分布漂移。
