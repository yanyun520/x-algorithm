# 05 · 内存数据结构设计

> 核心知识点:**索引与时间线分离**的两级存储、**引用最小化**(TinyPost)、多视图冗余、墓碑机制、保留策略与内存有界性。

源码位置:`thunder/posts/post_store.rs`。

---

## 1. 两级结构:主索引 + 轻量时间线

thunder 要回答的核心查询是:"给我关注列表里这 N 个作者最近的帖"。一个朴素设计是 `user_id → Vec<LightPost>`,但 `LightPost` 含十几个字段,一份帖数据会被每个视图重复存储。项目的设计:

```rust
posts: Arc<DashMap<i64, LightPost>>,                        // 全量数据,只存一份
original_posts_by_user: Arc<DashMap<i64, VecDeque<TinyPost>>>,  // 时间线只存引用

pub struct TinyPost {
    pub post_id: i64,
    pub created_at: i64,
}  // 16 字节
```

**原理**:**数据与索引分离**。全量 `LightPost` 在主索引中只存一份;每条用户时间线只存 16 字节的 `TinyPost`(ID + 时间戳)。查询时先遍历关注作者的时间线收集 `TinyPost`,再按 `post_id` join 主索引取全量。这本质上是数据库"堆表 + 二级索引"结构在内存中的复刻。

收益:同一帖子被"原创/视频"等多个视图引用时,冗余的只是 16 字节引用而非整条记录;时间线修剪(驱逐旧帖)也只动引用,不碰数据本体。

## 2. 多视图冗余:用空间换查询路径最短

针对不同的召回需求,写入时冗余到三条时间线:

```rust
if is_original {           // 非回复非转推
    original_posts_by_user.entry(author_id).or_default().push_back(tiny_post.clone());
} else {                   // 回复 + 转推
    secondary_posts_by_user.entry(author_id).or_default().push_back(tiny_post.clone());
}
if video_eligible {        // 视频帖(含"转推的源帖是视频"的继承)
    video_posts_by_user.entry(author_id).or_default().push_back(tiny_post);
}
```

查询方可以直接说"给我这些作者的原创帖"或"给我视频帖",**无需在线过滤**——过滤逻辑在写入时一次性完成。这是典型的**写时计算 vs 读时计算**的权衡:写多份(便宜,后台),读直取(快,在线)。

**业务语义固化的细节**——转推的视频继承:

```rust
if !video_eligible && post.is_retweet
    && let Some(source_post_id) = post.source_post_id
    && let Some(source_post) = self.posts.get(&source_post_id)
{
    video_eligible = !source_post.is_reply && source_post.has_video;
}
if post.is_reply { video_eligible = false; }   // 回复永远不算视频视图
```

"转推了一条视频帖,应视为视频内容;但回复不算"——这类规则在入库时判定,保证读路径零分支。

## 3. 写入路径的防御性设计

```rust
pub fn insert_posts(&self, mut posts: Vec<LightPost>) {
    let current_time = ...;
    posts.retain(|p| {
        p.created_at < current_time                                    // ① 丢弃未来时间戳
            && current_time - p.created_at <= self.retention_seconds   // ② 丢弃超期帖
    });
    posts.sort_unstable_by_key(|p| p.created_at);                      // ③ 批内排序
    Self::insert_posts_internal(self, posts);
}
```

- **① 未来时间戳防护**:上游脏数据(时钟漂移)会破坏时间线有序性,直接在入口丢弃;
- **② 保留期防护**:不让任何超期数据进入,配合定期 `trim_old_posts` 保证**内存占用有界**——这是内存数据库的生命线;
- **③ `sort_unstable`**:批内按时间排序后 push_back,使时间线近似有序;不追求全局严格有序(成本太高),因为查询本身按"最近 N 条"截断,近似有序已够用。**有序性要求要与查询需求匹配,过度保证是浪费**。

## 4. 删除与乱序:墓碑机制 + 启动对账

```rust
pub fn mark_as_deleted(&self, posts: Vec<TweetDeleteEvent>) {
    for post in posts {
        self.posts.remove(&post.post_id);                    // ① 主索引立即删
        self.deleted_posts.insert(post.post_id, true);       // ② 立墓碑
        // ③ 墓碑也进入一条"删除时间线",供定期清理用户时间线中的引用
        self.original_posts_by_user.entry(DELETE_EVENT_KEY).or_default()
            .push_back(TinyPost { post_id: post.post_id, created_at: post.deleted_at });
    }
}
```

- **为什么需要墓碑**:Kafka 事件可能乱序/重复——如果只有 `remove`,一条迟到的重复 create 事件会把已删的帖"复活";有了墓碑,`insert_posts_internal` 开头先查 `deleted_posts.contains_key(&post_id)`,直接拦截;
- **为什么删主索引不够**:用户时间线里的 `TinyPost` 引用还在——所以墓碑同时进入特殊时间线(`DELETE_EVENT_KEY`),由后台任务据此清理各用户时间线中的失效引用;
- **启动对账**(`finalize_init`):初始化数据加载完毕后,按墓碑表再统一清一次主索引——因为批量初始化阶段 create/delete 的到达顺序完全不可控,最后需要对账兜底。

**通用模式**:流式系统的删除必须假设"删除事件可能先于创建事件到达、创建事件可能重复到达",墓碑(tombstone)+ 定期对账(reconciliation)是标准解。

## 5. 去重的自然实现

```rust
let old = self.posts.insert(post_id, post);
if old.is_some() { continue; }  // 已存在 → 不再向时间线添加引用
```

利用 `DashMap::insert` 返回旧值的特性,一行代码实现幂等去重:重复事件不会导致时间线中出现重复引用。

## 6. 可迁移场景

- **实时排行榜 / 实时库存 / 会话存储**:主索引 + 轻量引用时间线的两级结构;
- **事件溯源系统**:墓碑 + 对账处理乱序与重复;
- **任何内存有界服务**:入口保留期过滤 + 后台定期修剪的双保险;
- **读多写多但查询模式固定**的服务:写时多视图冗余,读时零过滤。
