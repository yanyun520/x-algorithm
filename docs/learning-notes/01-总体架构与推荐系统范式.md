# 01 · 总体架构与推荐系统范式

> 核心知识点：工业级推荐系统的**两阶段范式**(召回 Retrieval → 精排 Ranking)、**双路召回**设计、微服务式组件职责划分。

---

## 1. 两阶段推荐范式

工业推荐系统面对的核心矛盾：**语料规模(百万~亿级)与在线延迟(百毫秒级)**。单一模型无法兼顾，因此拆成两级:

```
百万级语料 ──召回──▶ 千级候选 ──精排──▶ 百级结果 ──重排/合规──▶ 最终 Feed
   (快而粗,ANN 近似)      (慢而精,Transformer 全特征)      (业务规则)
```

x-algorithm 中的落地:

| 阶段 | 组件 | 实现 |
|------|------|------|
| 召回 | `PhoenixSource` + `ThunderSource` | 两塔模型(OON)+ 关注图内存查询(in-network) |
| 过滤 | `filters/` | 10 个顺序过滤器,在打分前砍掉无效候选 |
| 精排 | `PhoenixScorer` → `WeightedScorer` | Grok 系 Transformer 预测 15+ 动作概率,加权和为最终分 |
| 重排 | `AuthorDiversityScorer` → `OONScorer` → `TopKScoreSelector` | 多样性衰减、网外折扣、TopK 截断 |
| 合规 | `VFFilter` + `DedupConversationFilter` | 打分后可见性过滤(删除/暴力/垃圾) |

**学习要点**:昂贵操作要尽可能后置且作用于尽可能小的集合——过滤前置是为了省 ML 推理成本,VF 合规后置是因为它只对最终少量候选必要。

## 2. 双路召回(召回源互补)

推荐系统需要同时解决**相关性**与**发现性**:

- **In-Network(Thunder)**:用户关注账号的最新帖。保证 feed 的"社交相关性",来自社交图谱的显式信号;
- **Out-of-Network(Phoenix Retrieval)**:从全局语料中 ML 检索。保证"发现性",打破信息茧房。

两路**并行召回后合并**,统一进入同一打分器公平竞争。这是现代 feed 系统(Twitter、抖音、小红书)的标配结构。

```rust
// home-mixer/candidate_pipeline/phoenix_candidate_pipeline.rs
let sources: Vec<Box<dyn Source<ScoredPostsQuery, PostCandidate>>> =
    vec![phoenix_source, thunder_source];  // 双源注册,并行执行
```

`OONScorer` 再用 `OON_WEIGHT_FACTOR` 对网外内容做分数折扣,体现"同等质量下优先网内"的业务偏好。

## 3. 组件职责划分(微服务边界)

```
┌─────────────┐   gRPC    ┌──────────────────────────────┐
│  home-mixer │◀─────────▶│ thunder:InNetworkPostsService │
│ (策略编排)   │           │ (内存帖库,只负责存和查)       │
└──────┬──────┘           └──────────────────────────────┘
       │ gRPC
       ▼            ┌──────────────────────────────┐
       └───────────▶│ phoenix:Predict/Retrieval     │
                    │ (纯推理服务,无业务状态)        │
                    └──────────────────────────────┘
```

职责单一原则的体现:

- **thunder 不知道"推荐"**——它只维护"最近谁发了什么帖",提供按作者批量查询;
- **phoenix 不知道"过滤"**——它只对给定的 (用户, 候选集) 输出概率;
- **home-mixer 不做存储和推理**——只做策略编排:召回谁、过滤谁、怎么加权。

这种边界让每个服务可独立扩缩容、独立迭代:模型升级不影响存储,过滤规则调整不需要重训模型。

## 4. 读写分离与流批一体

thunder 内部是典型的 **CQRS(命令查询职责分离)**:

- **写路径**:Kafka 消费者持续摄入 create/delete 事件 → `PostStore`(流式写入,异步);
- **读路径**:gRPC `GetInNetworkPosts` → 按关注列表批量查时间线(在线查询,同步低延迟)。

两条路径共享同一个 `Arc<PostStore>`,通过 `DashMap` 分片锁实现无全局互斥的并发读写。写路径还设计了**背压机制**(见文档 04),防止摄入高峰饿死读请求——这是"流批一体"系统必须解决的资源竞争问题。

## 5. 可迁移场景

- 任何**搜索/推荐/广告**系统:两阶段范式 + 多路召回是通用骨架;
- **Feed 流产品**:双路召回(关注 + 发现)的平衡设计;
- **实时数仓**:thunder 的"Kafka 摄入 → 内存物化视图 → 低延迟查询"模式,可直接套用到实时排行榜、实时库存等场景。
